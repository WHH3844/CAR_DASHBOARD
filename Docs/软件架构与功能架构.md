# CAR_DASHBOARD 软件架构与功能架构

## 当前版本

当前建议版本命名：

```text
v0.4.0-rtos-split-dashboard
```

版本代号：`RTOS Split Dashboard`

该版本对应的工程状态是：PCB 一版硬件通路已经完成 bring-up，正式 Mini AUTOSAR-like 分层架构已经落地，FreeRTOS 默认开启拆分任务，Dashboard UI、CAN 矩阵、UDS 诊断、Dem 故障管理、NvM EEPROM 保存、RTC/SHT30/TPMS 和电源管理已经形成可演示闭环。

## 软件分层架构

项目采用轻量 AUTOSAR-like 分层设计，不追求完整 AUTOSAR 工具链和 ARXML 生成流程，但保留分层、接口隔离、服务化和可测试的工程思想。

```text
APP
  Dashboard / Display / Power / Key / Sensor / Diag / Logger
  |
RTE
  Signal / Service / Event
  |
BSW
  Services: EcuM / BswM / Dcm / Dem / NvM / Crc / LogM / Det
  Communication: CanIf / CanTrcv / CanSM / PduR / Com / CanTp / UartIf
  ECU Abstraction: LcdIf / BacklightIf / BuzzerIf / PowerIf / RtcIf / SensorIf / IoHwAb
  Memory: Eep / MemIf / SdIf / FatFsIf / SdramIf / SdramMgr
  |
MCAL
  Mcu / Port / Dio / Can / I2c / LcdTli / LcdSpi / Exmc / Sdio / Tim / Uart / Wdg / Pwm
  |
Hardware
  GD32F470/GD32F450 + SDRAM + RGB LCD + CAN + I2C + EEPROM + RTC + SHT30 + TF + Keys + Buzzer
```

核心边界：

- `APP` 不直接访问 MCU 寄存器、CAN 字节、EEPROM 地址或 LCD framebuffer。
- `RTE` 负责信号快照、服务转发和事件发布，是 APP 和 BSW 的隔离面。
- `BSW` 负责通信、诊断、存储、故障、电源、显示抽象等基础服务。
- `MCAL` 负责 GD32 片上外设和板级硬件资源访问。
- `Config` 固化 CAN ID、DID、DTC、NvM 地址、调度周期和报警阈值。

## 启动与生命周期架构

当前入口链路：

```text
main.c
  -> EcuM_Init()
     -> Os_Init()
     -> 早期 PWR_HOLD 自锁
     -> LogM_Init()
     -> Rte_Init()
     -> NvM_Init()
     -> Dem_Init()
     -> SdramIf_Init()
     -> LcdIf_Init()
     -> BacklightIf/BuzzerIf
     -> Dcm/CanTp/Com/CanIf/CanSM
     -> App_Power/App_Key/App_Dashboard/App_Display/App_Sensor/App_Diag/App_Logger
  -> EcuM_MainLoop()
     -> Os_Start()
```

`EcuM` 状态机：

| 状态 | 含义 |
|---|---|
| `OFF` | 尚未进入启动流程或已经掉电 |
| `BOOT` | 早期上电保持阶段 |
| `SELF_TEST` | BSW/RTE/硬件抽象初始化和关键外设自检 |
| `RUN` | 正常运行，周期任务可以调度 |
| `SLEEP_PREPARE` | 收到关机请求，保存 NvM/Dem 并准备断电 |
| `FAULT` | 关键初始化失败，不进入业务调度 |

关机链路：

```text
长按 KEY_POWER
  -> App_Power 置位 shutdown request
  -> EcuM_LifecycleMainFunction()
  -> 关闭蜂鸣器和背光
  -> Dem_SaveNow()
  -> NvM_WriteAll()
  -> PowerIf_Shutdown()
  -> 拉低 PWR_HOLD
```

## FreeRTOS 任务架构

默认配置：

```c
#define APP_CFG_USE_FREERTOS         1u
#define APP_CFG_FREERTOS_SPLIT_TASKS 1u
```

任务划分：

| 任务 | 周期 | 优先级 | 主要入口 | 职责 |
|---|---:|---:|---|---|
| `CanTask` | 10ms | 4 | `EcuM_ComMainFunction()` | CAN 接收、CanSM、Com、Dcm |
| `AppFastTask` | 10ms | 3 | `EcuM_AppFastMainFunction()` | 电源、按键、Dashboard、应用诊断 |
| `DisplayTask` | 500ms | 2 | `EcuM_DisplayMainFunction()` | LCD 局部刷新和背光同步 |
| `SensorTask` | 1000ms | 1 | `EcuM_SensorMainFunction()` | RTC 和 SHT30 读取 |
| `NvMTask` | 100ms | 1 | `EcuM_NvMMainFunction()` | NvM/Dem 后台维护 |
| `LoggerTask` | 1000ms | 1 | `EcuM_LoggerMainFunction()` | 串口 heartbeat |
| `EcuM` | 10ms | 3 | `EcuM_LifecycleMainFunction()` | 生命周期和关机保存 |

任务拆分原则：

- 通信栈保持在 `CanTask` 内串行运行，避免 `CanIf/Com/Dcm/CanTp` 状态并发访问。
- RTE 读写使用短临界区，只保护内存快照复制。
- I2C0 总线使用 mutex，串行化 EEPROM、RTC、SHT30 等设备访问。
- NvM/Dem 周期维护和关机保存使用 mutex，避免写 EEPROM 时状态交叠。
- 如需排查多任务问题，先把 `APP_CFG_FREERTOS_SPLIT_TASKS` 改为 `0u`；如需排查 RTOS 本身，再把 `APP_CFG_USE_FREERTOS` 改为 `0u`。

## 功能架构

### 1. CAN 业务通信

接收链路：

```text
CAN1
  -> Mcal/Can
  -> CanIf_MainFunction()
  -> PduR_RxIndication()
  -> Com_RxIndication()
  -> Rte_Write_xxx()
  -> App_Dashboard / App_Display / Dcm
```

当前业务报文：

| CAN ID | 方向 | 功能 |
|---|---|---|
| `0x321` | 输入 | 车速、转速、油量、水温、外温、电压 |
| `0x322` | 输入 | 点火、档位、MIL/ABS/AIR/BRK 告警位 |
| `0x323` | 输入 | 四轮胎压和胎温 |
| `0x324` | 输入 | 主题、语言、单位制、背光、音量、续航、外部时间 |
| `0x325` | 输出 | 仪表状态、报警、静音、模拟模式、动力 CAN 有效 |
| `0x326` | 输出 | DTC 数量、诊断会话、动力 CAN 有效 |
| `0x327` | 输出 | 用户按键事件 |
| `0x328` | 输出 | 日志状态和运行秒数 |
| `0x440` | 输出 | 简化 NM/RUN 心跳 |

### 2. UDS 诊断

诊断链路：

```text
0x700 / 0x7DF
  -> CanIf
  -> PduR
  -> CanTp
  -> Dcm
  -> Dem / NvM / RTE
  -> CanTp
  -> 0x708
```

当前支持服务：

| SID | 服务 | 当前实现 |
|---|---|---|
| `0x10` | DiagnosticSessionControl | 默认会话和扩展会话 |
| `0x22` | ReadDataByIdentifier | 启动次数、车速、转速、电压、RTC、硬件/软件版本 |
| `0x19` | ReadDTCInformation | DTC 数量和首个匹配 DTC |
| `0x14` | ClearDiagnosticInformation | 扩展会话下清除全部 DTC |
| `0x3E` | TesterPresent | 保持诊断会话 |

### 3. Dem 故障管理

`Dem` 管理 20 个教学版 DTC，包含当前失败位、confirmed 位、warning indicator 位和发生次数。故障状态变化后置 dirty，周期任务限频保存到 NvM；关机时 `EcuM` 调用 `Dem_SaveNow()` 兜底保存。

故障来源示例：

- CAN bus-off、CAN 收发器错误、动力 CAN 超时。
- EEPROM 通信或 CRC 失败。
- RTC 通信失败或时间非法。
- SHT30 通信失败。
- SDRAM/LCD 初始化失败。

### 4. NvM 非易失性存储

底层 EEPROM 是 FT24C16A，当前 NvM 块：

| 块 | 地址 | 内容 |
|---|---:|---|
| `BOOT_INFO` | `0x0700` | 启动次数和 reset 记录 |
| `SYSTEM_CONFIG` | `0x0720` | 背光、蜂鸣器、主题等配置 |
| `DEM_STATUS` | `0x0740` | DTC 状态和发生次数 |

每个块格式：

```text
magic + version + length + crc16 + payload
```

### 5. LCD 显示

显示链路：

```text
RTE 快照
  -> App_Display
  -> LcdIf
  -> LcdTli / SDRAM framebuffer
  -> RGB LCD
```

当前界面功能：

- 左侧 RPM 表盘。
- 右侧车速表盘。
- 中央大号车速和档位。
- 顶部 CAN/SIM 状态和告警灯。
- 底部燃油、水温、电池电压、时间、座舱温湿度、TPMS。
- 背光等级可由 `0x324` 动态同步。

显示刷新策略：

- 上电后只清一次全屏。
- 动态区域按缓存判断是否需要重画。
- 表盘擦旧指针、补刻度、画新指针，减少整屏闪烁。

### 6. 传感器与时间

`App_Sensor` 通过 `RtcIf` 和 `SensorIf` 周期读取：

- DS3231 RTC：1s 刷新，时间非法或 OSF 置位时可按编译时间自动校准。
- SHT30：1s 刷新，温湿度使用 x100 定点数写入 RTE。

### 7. 按键、蜂鸣器和电源

- `KEY1`：切换模拟车速/转速模式。
- `KEY2`：切换蜂鸣器静音。
- `KEY3`：清零当前仪表动力域显示值。
- `KEY_POWER` 长按：请求关机，由 `EcuM` 统一保存 NvM/Dem 后断电。

蜂鸣器策略：

- 按键触发 80ms 确认音。
- 超速或高转速时，若未静音，按 500ms 周期、80ms 占空输出报警音。

## 当前架构评价

当前工程已经从“测试程序集合”进化为“可解释、可演示、可继续扩展”的嵌入式软件架构：

- 分层边界清楚：APP、RTE、BSW、MCAL 职责可讲清。
- 功能闭环完整：输入 CAN、显示仪表、输出状态、诊断读取、故障保存、关机保存都有路径。
- 调试回退明确：拆分任务、单 EcuM 任务、裸机 super loop 三档可切换。
- 后续扩展方向清晰：完整 ISO-TP 多帧、FatFs 日志、主题/语言/单位制 UI、更多 DID/DTC 快照、显示双缓冲或 VSYNC 同步。
